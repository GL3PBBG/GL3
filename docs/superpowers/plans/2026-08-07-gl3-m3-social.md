# GL3 M3 — Social Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the social layer on top of the M0–M2 core loop: gangs (create/invite/roles/bank/logs), threaded mail, a notification feed, public profiles, and broadcast game news — with gang bank transfers fully ledgered and gang invitees notified live over the existing WS gateway.

**Architecture:** Every social mutation is a Fastify HTTP handler that validates with zod (body **and** route params), runs one Postgres transaction, and — for the six user-facing events this milestone wires up (`gang.created`, `gang.memberJoined`, `gang.memberLeft`, `mail.received`, `notification.created`, `news.posted`) — publishes a validated `GameEvent` to `game:events` strictly after that transaction commits. The already-built WS gateway (`apps/server/src/ws/gateway.ts`, spec §2.2) fans each event out purely by `event.audience`, resolving `{kind:"gang"}` via the existing `gang_members` table; nothing in this plan touches the gateway. Gang bank transfers reuse the M1 ledger (`applyBalanceChange`) plus a new, symmetric gang-side primitive (`applyGangBalanceChange`) so a transfer between a player and a gang is two ledger rows in one transaction, both rows written under a single deterministic lock order.

**Tech Stack:** Same as M0–M2 — Node 22 LTS (ESM), TypeScript strict, Fastify 5, Drizzle ORM + `postgres` driver, PostgreSQL 16, Redis 7 (pub/sub only in this milestone — no new BullMQ queues), zod, vitest. No new runtime dependencies.

## Global Constraints

These restate the constraints from the M0/M1 plan (still binding) plus the ones specific to this milestone. Do not restate them per task; do not violate them.

- **All 32 tables already exist** (spec §2.5). This plan adds gameplay, not tables. The one genuinely missing piece — a way to ledger a gang's balance — is an explicit **column** migration on the existing `transactions` table (Task 1), not a new table.
- **Bigint defaults are always `` .default(sql\`0\`) ``, never `.default(0n)`** — drizzle-kit's serialiser crashes on a literal BigInt (drizzle-orm #1879/#2382/#3609, unfixed as of 0.45.2). Every new bigint-bearing column in this plan follows the pattern already used throughout `apps/server/src/db/schema/`.
- **Every cash/bank/points mutation is an append-only `transactions` insert + a balance update in ONE Postgres transaction.** This now also covers a gang's `bank`/`cash` columns via `applyGangBalanceChange` — same rule, same table, an owner discriminator instead of a second ledger table.
- **Any operation mutating two parties locks rows with `SELECT … FOR UPDATE` in a single consistent order.** A gang bank transfer touches two different tables (`gangs`, `player_stats`); Task 1 adds `lockGangAndPlayerForUpdate`, which locks both, in the same order regardless of transfer direction, before either side is touched. As in the M1 ledger, the ordering guarantee comes from the SQL the lock queries emit, not from any JS-side sort alone — the queries below are written to make that observable.
- **Any worker that mutates the economy needs an idempotency key tied to the job, not just a seed.** This plan does **not** introduce a new BullMQ worker (see "Decisions taken" — gang bank transfers are synchronous, for reasons argued there), so this constraint has no new worker to apply to. It is restated because the reasoning that ruled out a worker here is exactly the reasoning this constraint encodes, and a future milestone that *does* add an economy-mutating worker must follow the same `job_id`-unique-column pattern used by `crime_log.job_id`.
- **Money is `bigint`, everywhere, no floating point.** Gang `bank`/`cash` are `bigint` already (spec §2.5); nothing here changes that.
- **New event types go in `GameEventSchema` in `packages/shared` — but this milestone invents none.** `gang.created`, `gang.memberJoined`, `gang.memberLeft`, `mail.received`, `notification.created`, `news.posted` are already declared in `packages/shared/src/events.ts`. Every task below wires up one or more of these; none adds a new discriminant.
- **The WS gateway routes purely on `event.audience`.** No task in this plan modifies `apps/server/src/ws/gateway.ts`. If a feature needs live delivery, it publishes an event with the right `audience` and lets the existing gateway do the rest.
- **TypeScript strict, no `any` in `packages/*`, zod on every external boundary (HTTP body AND route params), ESM `.js` import extensions, Conventional Commits.**
- **Tests hit real Postgres and Redis, no mocks for DB/queue paths.** Every test file gets its own isolated, migrated database automatically via `apps/server/test/helpers/isolated-db.setup.ts`, and the shared register/login rate-limit buckets are cleared before every test via `apps/server/test/helpers/rate-limit-isolation.setup.ts` — both are already wired into `vitest.workspace.ts`; no test file in this plan needs to know either exists. Export `DATABASE_URL` and `REDIS_URL` before running tests.
- **Scope discipline.** SPEC §6 M3 is "Gangs (create/invite/roles/bank/logs), mail, notifications, profile, game news." No gang directory/search listing, no forum, no casino — those stay out of scope exactly as the M0/M1 plan kept M2's features out of M1.

## Decisions taken (spec-permitted, stated for the record)

1. **Gang balances are ledgered by extending `transactions`, not by adding a second ledger table.** `transactions.player_id` becomes nullable, a nullable `transactions.gang_id` (FK → `gangs.id`) is added, and a `CHECK` constraint enforces exactly one of the two is set per row. A gang bank transfer is therefore two ordinary `transactions` rows — one player-owned, one gang-owned — written in the same Postgres transaction, joinable by a shared `ref_id`. This reuses the existing "sum(ledger) == balance" invariant per owner instead of inventing gang-specific bookkeeping.
2. **Gang bank deposit/withdraw are synchronous HTTP handlers, not a BullMQ worker.** The crime slice needs a worker for one reason: randomness must resolve exactly once and must not be re-rollable on retry (spec §7). A gang bank transfer has no randomness — it is a deterministic double-entry write. Routing it through BullMQ would buy nothing and would cost real complexity: an async job that can fail on `InsufficientFundsError`/insufficient gang funds has no clean way to report that failure back to the (already-departed) HTTP response, forcing either silent job failure or an event type SPEC doesn't ask for. A direct `db.transaction(...)` inside the HTTP handler — the same shape M1's `auth/routes.ts` already uses for register/login — reports success or a 400 synchronously, and is exactly as safe: there is no automatic retry mechanism to double-credit, because there is no queue. `lockGangAndPlayerForUpdate` still enforces a single deterministic lock order, per the Global Constraints.
3. **SPEC §6's two M3 checkmarks are separate features, not one flow.** "gang bank transfers ledgered" is a ledger-correctness property (proven by an invariant test, decision 2 above). "WS notifies invitees live" is the gang **invite** flow: inviting a player inserts a `notifications` row for them and publishes the already-declared `notification.created` event with `audience: {kind:"player"}`. No new event name is needed for either half.
4. **Gang permission bypass for boss/underboss mirrors V2's `G_boss`/`G_underboss`.** `gang_permissions` (spec §1.2: no gang column in V2, a real `gang_id` in GL3) governs *delegated* permissions; the boss and underboss always pass every permission check without needing a row, exactly as V2's leadership always could.
5. **`game_news` reuses the existing `role_module_access` table for posting rights**, rather than adding a new "is staff" flag — a role with `module_key = 'news'` or the `'*'` wildcard (spec §1.2, already preserved in `role_module_access`) may post. Reading news requires no auth (a public bulletin board).
6. **No gang directory/search endpoint.** SPEC's M3 line doesn't ask for one; adding it would be scope creep the M0/M1 plan explicitly warns against repeating.

- [ ] **Step 5: Write the routes**

`apps/server/src/game/notifications/routes.ts`:

```ts
import { and, desc, eq } from "drizzle-orm";
import type { FastifyInstance, FastifyReply, FastifyRequest } from "fastify";
import { z } from "zod";
import { IdSchema } from "@gl3/shared";
import type { Db } from "../../db/client.js";
import { notifications } from "../../db/schema/index.js";

const NotificationParamsSchema = z.object({ notificationId: IdSchema });

export function registerNotificationRoutes(
  app: FastifyInstance, db: Db,
  requireAuth: (request: FastifyRequest, reply: FastifyReply) => Promise<void>,
): void {
  app.get("/api/notifications", { preHandler: requireAuth }, async (request, reply) => {
    const playerId = request.playerId;
    if (!playerId) return reply.code(401).send({ error: "unauthorized" });

    const rows = await db.select().from(notifications)
      .where(eq(notifications.playerId, playerId))
      .orderBy(desc(notifications.createdAt));

    return reply.send({
      notifications: rows.map((n) => ({
        id: n.id,
        body: n.body,
        readAt: n.readAt?.toISOString() ?? null,
        createdAt: n.createdAt.toISOString(),
      })),
    });
  });

  app.post("/api/notifications/:notificationId/read", { preHandler: requireAuth }, async (request, reply) => {
    const playerId = request.playerId;
    if (!playerId) return reply.code(401).send({ error: "unauthorized" });

    const params = NotificationParamsSchema.safeParse(request.params);
    if (!params.success) return reply.code(400).send({ error: "invalid_request" });

    const [updated] = await db.update(notifications)
      .set({ readAt: new Date() })
      .where(and(eq(notifications.id, params.data.notificationId), eq(notifications.playerId, playerId)))
      .returning({ id: notifications.id });

    if (!updated) return reply.code(404).send({ error: "notification_not_found" });
    return reply.code(204).send();
  });
}
```

### Task 2: Gang balance ledger — schema extension and primitives

Spec §1.2/§2.5: a gang has two balances, `bank` and `cash`. This task gives them the same append-only-ledger guarantee player balances already have, by generalising `transactions` to accept a gang owner instead of a player owner.

**Files:**
- Modify: `apps/server/src/db/schema/economy.ts`
- Modify: `apps/server/src/economy/ledger.ts`
- Create: `apps/server/drizzle/000N_*.sql` (drizzle-kit auto-names it; renamed below), modify `apps/server/drizzle/meta/_journal.json`
- Test: `apps/server/test/gang-ledger.test.ts`

**Interfaces:**
- Consumes: `gangs`, `playerStats`, `transactions` tables; `Tx`, `lockPlayersForUpdate`, `applyBalanceChange` (M1).
- Produces:
  - `type GangBalanceKind = "cash" | "bank"`
  - `interface GangBalanceChange { gangId: string; amount: bigint; kind: GangBalanceKind; reason: string; refId?: string }`
  - `applyGangBalanceChange(tx: Tx, change: GangBalanceChange): Promise<bigint>` — the gang-side sibling of `applyBalanceChange`; returns the new balance.
  - `lockGangsForUpdate(tx: Tx, gangIds: string[]): Promise<void>` — same ascending-order pattern as `lockPlayersForUpdate`.
  - `lockGangAndPlayerForUpdate(tx: Tx, gangId: string, playerId: string): Promise<void>` — locks both rows, in a single deterministic order (string-compare the two ids), before either side of a transfer is touched.
  - `InsufficientGangFundsError` — thrown when a gang debit would go negative.
  - Schema: `transactions.playerId` nullable, `transactions.gangId` nullable (FK → `gangs.id`, `onDelete: cascade`), a `CHECK` constraint that exactly one of the two is set.

    expect(await db.select().from(transactions)).toHaveLength(0);

    await db.update(playerStats).set({ cash: 5_000n }).where(eq(playerStats.playerId, playerId));

        await lockGangAndPlayerForUpdate(tx, gangId, playerId);
        if (deposit) {

          await applyGangBalanceChange(tx, { gangId, amount, kind: "bank", reason: "test.gang-transfer" });

          await applyGangBalanceChange(tx, { gangId, amount: -amount, kind: "bank", reason: "test.gang-transfer" });
          await applyBalanceChange(tx, { playerId, amount, kind: "cash", reason: "test.gang-transfer" });
        }

  // player_stats, applyGangBalanceChange locks gangs — two different tables.
  // Without one deterministic order up front, a deposit (naively: lock gang,
  // then player) and a withdrawal (naively: lock player, then gang) running
  // concurrently could each hold one lock and wait on the other — a genuine
  // Postgres deadlock (40P01), not a timing flake. 40 concurrent, alternating
  // transfers between the SAME gang/player pair is enough to hit that window
  // reliably if the ordering were direction-dependent.

      await lockGangAndPlayerForUpdate(tx, gangId, playerId);
      if (direction === "deposit") {
        await applyBalanceChange(tx, { playerId, amount: -1n, kind: "cash", reason: "test.gang-transfer" });
        await applyGangBalanceChange(tx, { gangId, amount: 1n, kind: "bank", reason: "test.gang-transfer" });
      } else {
        await applyGangBalanceChange(tx, { gangId, amount: -1n, kind: "bank", reason: "test.gang-transfer" });
        await applyBalanceChange(tx, { playerId, amount: 1n, kind: "cash", reason: "test.gang-transfer" });
      }
    });

    const attempts = Array.from({ length: 40 }, (_, i) => attempt(i % 2 === 0 ? "deposit" : "withdraw"));
    await expect(Promise.all(attempts)).resolves.toBeDefined();
  });

  // Proves the lock order is genuinely deterministic regardless of which id is
  // lexicographically smaller — captures the literal SQL each call sends via
  // the `postgres` driver's `debug` hook, the same technique ledger.test.ts
  // uses for lockPlayersForUpdate.

      expect(gangFirst).toBe(gangId < playerId);

```ts
import { gangs } from "../db/schema/index.js";

export type GangBalanceKind = "cash" | "bank";

export interface GangBalanceChange {
  gangId: string;
  amount: bigint;
  kind: GangBalanceKind;
  reason: string;
  refId?: string;
}

export class InsufficientGangFundsError extends Error {
  constructor(readonly gangId: string, readonly kind: GangBalanceKind) {
    super(`insufficient gang ${kind} for gang ${gangId}`);
    this.name = "InsufficientGangFundsError";
  }
}

const gangColumn = { cash: gangs.cash, bank: gangs.bank } as const;

/** Same ascending-id-order guarantee as lockPlayersForUpdate, applied to gangs. */
export async function lockGangsForUpdate(tx: Tx, gangIds: string[]): Promise<void> {
  const unique = [...new Set(gangIds)].sort();
  if (unique.length === 0) return;
  await tx.select({ id: gangs.id })
    .from(gangs)
    .where(inArray(gangs.id, unique))
    .orderBy(asc(gangs.id))
    .for("update");
}

/** The gang-side sibling of applyBalanceChange. Same contract: call inside an existing transaction, returns the new balance. */
export async function applyGangBalanceChange(tx: Tx, change: GangBalanceChange): Promise<bigint> {
  await lockGangsForUpdate(tx, [change.gangId]);

  const target = gangColumn[change.kind];
  const [current] = await tx.select({ value: target })
    .from(gangs)
    .where(eq(gangs.id, change.gangId));

  if (!current) throw new Error(`gang missing for ${change.gangId}`);

  const next = current.value + change.amount;
  if (next < 0n) throw new InsufficientGangFundsError(change.gangId, change.kind);

  await tx.update(gangs)
    .set({ [change.kind]: next })
    .where(eq(gangs.id, change.gangId));

  await tx.insert(transactions).values({
    id: uuidv7(),
    gangId: change.gangId,
    playerId: null,
    amount: change.amount,
    balanceKind: change.kind,
    reason: change.reason,
    refId: change.refId ?? null,
  });

  return next;
}

/**
 * Locks a gang row and a player_stats row in a single global order — the two
 * live in different tables, so applyBalanceChange's and applyGangBalanceChange's
 * own single-row locks can't establish cross-table ordering on their own.
 * String-comparing the two UUIDs gives a total order that is the same
 * regardless of which side (deposit vs withdraw) is conceptually "first",
 * which is what actually prevents the deadlock — see gang-ledger.test.ts.
 */
export async function lockGangAndPlayerForUpdate(tx: Tx, gangId: string, playerId: string): Promise<void> {
  if (gangId < playerId) {
    await lockGangsForUpdate(tx, [gangId]);
    await lockPlayersForUpdate(tx, [playerId]);
  } else {
    await lockPlayersForUpdate(tx, [playerId]);
    await lockGangsForUpdate(tx, [gangId]);
  }
}
```

export type GangPermission = typeof GANG_PERMISSIONS[number];

/**
 * V2's gangPermissions table had no gang column at all — membership implied
 * it (spec §1.2). GL3's gang_permissions carries a real gang_id, but the
 * boss/underboss bypass below preserves V2's effective behaviour: leadership
 * always had every permission, whether or not a gangPermissions row existed.
 */
export async function hasGangPermission(
  db: Db | Tx, gangId: string, playerId: string, permission: GangPermission,
): Promise<boolean> {
  const [gang] = await db.select({ boss: gangs.bossPlayerId, underboss: gangs.underbossPlayerId })
    .from(gangs).where(eq(gangs.id, gangId));
  if (!gang) return false;
  if (gang.boss === playerId || gang.underboss === playerId) return true;

  const [row] = await db.select({ permission: gangPermissions.permission })
    .from(gangPermissions)
    .where(and(
      eq(gangPermissions.gangId, gangId),
      eq(gangPermissions.playerId, playerId),
      eq(gangPermissions.permission, permission),
    ));
  return row !== undefined;
}

      if (!existing) return reply.code(403).send({ error: "forbidden" });

      threadId = uuidv7();

    await db.insert(mailMessages).values({
      id, threadId, senderId: playerId, recipientId: recipient.id,
      subject: parsed.data.subject, body: parsed.data.body,

      mailId: id, recipientId: recipient.id, subject: parsed.data.subject,

    const playerId = request.playerId;
    if (!playerId) return reply.code(401).send({ error: "unauthorized" });

    const rows = await db.select().from(mailMessages).where(eq(mailMessages.recipientId, playerId)).orderBy(desc(mailMessages.createdAt));
    const senderIds = [...new Set(rows.map((r) => r.senderId).filter((id): id is string => id !== null))];

      ? await db.select({ id: players.id, username: players.username }).from(players).where(or(...senderIds.map((id) => eq(players.id, id))))

    const nameById = new Map(senders.map((s) => [s.id, s.username]));

    return reply.send({ mail: rows.map((r) => toDto(r, r.senderId ? nameById.get(r.senderId) ?? null : null)) });

    const params = ThreadParamsSchema.safeParse(request.params);
    if (!params.success) return reply.code(400).send({ error: "invalid_request" });

        eq(mailMessages.threadId, params.data.threadId),
        or(eq(mailMessages.senderId, playerId), eq(mailMessages.recipientId, playerId)),
      ))
      .orderBy(mailMessages.createdAt);

    return reply.send({ mail: rows.map((r) => toDto(r, null)) });

      .returning({ id: mailMessages.id });

    if (!updated) return reply.code(404).send({ error: "mail_not_found" });
    return reply.code(204).send();
  });

      payload: { username: "Sonny" },

    const inviteFrame = ServerFrameSchema.parse(await invited);
    expect(inviteFrame.kind).toBe("event");
    if (inviteFrame.kind !== "event") throw new Error("unreachable");
    expect(inviteFrame.event.type).toBe("notification.created");
    recruitSocket.close();

    const [invite] = await db.select().from(gangInvites).where(eq(gangInvites.invitedPlayerId, recruitId));
    const acceptRes = await app.inject({

      payload: { amount: "400" },

    expect(withdrawRes.json().bank).toBe("600");
